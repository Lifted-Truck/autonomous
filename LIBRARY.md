[L0001] A `sed` on `/etc/ssh/sshd_config` is not hardening on a cloud image — drop-ins are Included FIRST and OpenSSH is first-value-wins | canonical | added: 2026-08-14 | tags: cloud-image | lesson: Ubuntu's stock `sshd_config` `Include`s `sshd_config.d/*.conf` near the TOP, and OpenSSH takes the FIRST value it meets for each keyword. So a hardening script that `sed`s `PasswordAuthentication no` into the main file is silently overridden by cloud-init's `50-cloud-init.conf` (`PasswordAuthentication yes`), and the file LOOKS hardened while the effective config is not. Write your own `00-<project>-hardening.conf` (sorts first, so it wins over anything cloud-init writes later) and ASSERT the effective config with `sshd -T`, never by reading the file — prove the result, not the artifact. Generalizes to every cloud-image box the fleet deploys. | evidence: life-os-app VPS, verified live 2026-08-14 in response to autonomous-lifeos-001: `bootstrap.sh`'s sed had run, `sshd -T` showed `passwordauthentication yes`; tens of thousands of failed-password attempts in 30d had been hitting an endpoint the script believed was closed (bounded by a locked deploy-account password + `PermitRootLogin no`, so no breach — a defense-in-depth gap). Fixed with the 00- drop-in + `sshd -T` assertion in `bootstrap.sh`; password auth verified refused from outside. Filed by the Life-OS resident via autonomous-lifeos-001 response-1; Promoted from life-os-app#L0002 (their copy: tier candidate, tags deploy-ops/security). | falsifier: on a stock Ubuntu cloud image with a conflicting `50-cloud-init.conf`, `sshd -T` shows the sed'd main-file value taking effect. | origin: life-os-app#L0002

[L0002] A gate that has never fired against known-bad input is not known to be a gate — and `git grep -E` is POSIX ERE, so `\s`, `\d`, `\b` all silently match nothing | canonical | added: 2026-08-14 | tags: gate-blindness, detector-calibration | lesson: `git grep -E` does not support Perl-class escapes. A pattern using `\s`, `\d` or `\b` does not error; it matches NOTHING, and the gate ships permanently green. Three independent instances in five weeks: `\s` in the first leak_scan (all findings were coming from the username pattern alone), then `\b` in life-os-app's ip_gate (would never have flagged the very IP it was written for). The only defense that catches this class is procedural: before trusting any new detector, plant a KNOWN-BAD line and watch it fire, plant a KNOWN-GOOD near-miss and watch it stay quiet, then run the clean tree. Comment the trap at the pattern site — the next agent will "simplify" it back. | evidence: leak_scan.py 2026-07-13 (dead absolute-path detection, caught only by testing against a known-bad); life-os-app `verify` ip_gate 2026-08-14 (planted the real leaked IP, 0 hits, root cause `\b`). Antiphon L0001 records the same rule from the consumer side. | falsifier: a `git grep -E` invocation where `\s`/`\d`/`\b` demonstrably matches — would mean git grep gained PCRE by default and this rule can retire (check `git grep -P` availability first; that is a different flag).

[L0003] The MCP Python SDK went 2.0 with the 2026-07-28 spec revision and moved `mcp.server.fastmcp`; a `>=1.0` floor breaks every fresh install while old venvs keep working | candidate | added: 2026-08-14 | tags: mcp-sdk | lesson: `mcp>=1.0` in requirements resolves to 2.0.0 on a fresh install; the 1.x `FastMCP` import path is gone and the server fails at import. Local venvs created before the release keep working, so the break is invisible until CI or a new machine — exactly the "works on my venv" shape. Working migration (life-os-app): try `from mcp.server.mcpserver import MCPServer as FastMCP` first, fall back to `from mcp.server.fastmcp import FastMCP` — same `.tool()`/`.run()` API, so one file runs on both. Prove it BOTH ways (fresh 2.0 venv AND the old pinned one) before dropping any pin. THE SHIM IS SAFE ONLY ON THE SHARED API SURFACE — `.tool()` decorator and `.run()` with stdio default. A server that reached into 1.x-specific FastMCP internals is NOT rescued by the fallback and needs a real migration. So the retrofit check for each of the ten remaining MCP-server repos is "does the server touch anything beyond `@tool`/`.run()`?", not "does the import resolve" — the second passes on a shim that will fail at first call. | evidence: (fleet-origin, first proof-site life-os-app) CI first run 2026-08-14 (`ModuleNotFoundError: No module named 'mcp.server.fastmcp'` on the runner; local venv on 1.28.1 fine); migration verified 8/8 tools registering on 2.0.0 fresh + 246 tests green on both. | falsifier: an MCP-server repo in the fleet with `mcp>=1.0` that installs clean on 2.x without the fallback — would mean it never used the moved path, and this is a per-import-path issue, not a fleet-wide one.

[L0004] Consumer-authored contract tests catch the dialect the provider does not write; own-corpus fixtures cannot | candidate | added: 2026-08-14 | tags: protocol | lesson: A detector or parser tested only against fixtures drawn from its own repo's files is tested only against the conventions that repo already follows. `ball_scan` matched the `ball:` field by whole string because autonomous writes bare tokens; FOUNDATIONS and Tonality write `ball: provider (please review…)`, so every annotated obligation ON autonomous read as not-ours — a false negative in the check whose job was not losing work — and no fixture buildable from autonomous's own mailbox would ever have shown it. INTEGRATIONS already says contract tests are consumer-authored; this is the mechanism-level reason WHY that rule is load-bearing, not etiquette. | evidence: ball_scan.py 2026-08-09, found by answering "is there a HYPERSAW brief?" against FOUNDATIONS' mailbox; fixed with `_ball_token` + tests seeded from the OTHER repos' forms. dispatch-001's four-named-findings fixture is the positive case: it pinned granularity the provider would not have thought to. | falsifier: a provider-authored fixture set that surfaces a consumer's dialect without any consumer input — possible only if the provider deliberately samples every consumer's corpus, which is the consumer-authorship rule by another name.

[L0005] A detector shares assumptions with the thing it measures, so its first run against a foreign corpus is the only cheap test of those assumptions — and a must-read-zero check needs a paired corruption or it cannot fail | canonical | added: 2026-08-18 | tags: detector-calibration, gate-blindness | lesson: Two halves, both learned the same day. (a) `library_validate` produced three false positives on first contact with real files, and all three were the detector assuming ITS OWN conventions: the local `L\d{4}` reference shape applied to `origin` (which the contract gives `<child>#Lxxxx`), an unknown labelled segment continuation-joined instead of routed to `extra`, and one prose value split on its own commas into three findings for one defect. None was visible against fixtures the author wrote, because the fixtures shared the assumptions. (b) The obvious control — "our own corpus must read zero" — CANNOT FAIL: if the file-level path becomes a no-op it returns zero and passes. Measured: the suite passed 12/12 against a deliberately neutered `validate_file`, because every other test exercised the entry-level path. A must-read-zero assertion is only meaningful PAIRED with a corruption of the same file that must read non-zero. | evidence: kit/gates/library_validate.py, 2026-08-18 — three false positives on HYPERSAW's LIBRARY and autonomous's own on first run; the inertness hole demonstrated by monkeypatching `validate_file` to return [] and observing 12/12 green; paired control added and re-proven to fail against the same neutered function. Control suggested by HYPERSAW (round 4), who also supplied the foreign corpus that exposed (a). | falsifier: a detector whose first run against a corpus written by someone else produces no assumption-level false positives AND whose must-read-zero control, when the checked function is stubbed inert, still fails. Both halves must hold; either one alone is the trap.
[L0006] A probe that runs the target's own oracle inherits the oracle's side effects — "left untouched" must be true of every file the oracle writes, not only the files the probe wrote | canonical | added: 2026-08-18 | tags: probe-side-effects, effective-state | lesson: `currency.py`'s gate-fires probe plants a known-bad file and runs the target's `./verify fast`. A correctly firing gate exits 1 — and the target's `record()` writes that exit into `.harness/last-verify.json` and deletes `.harness/dirty`. The probe removed its plant and called the repo untouched; the repo's Stop hook then blocked on a red that was actually the probe PASSING, with a clean tree, seconds after the resident's own green close — a symptom designed to look like a defect. The fix is symmetric with the plant: snapshot every file the oracle writes before, restore byte-for-byte after (including "absent"), in the same try/finally. General form: whenever a check invokes a subprocess that has its own record-keeping, the check's cleanup contract extends to that record-keeping. | evidence: juce-rag, 2026-08-18 — record read `exit:1 / 04:16:00Z` seconds after a green close, re-run green at 04:16:17; found by the first live Step 6 verification (retrofit_verify → currency → their verify). Fixed in kit 2.2.2 with `_harness_snapshot`/`_harness_restore`; the new test fails against the prior code with the exact `exit:1` overwrite juce-rag saw. | falsifier: a probe that runs a target's oracle and, on a target whose oracle has side effects, leaves every such file byte-identical (or identically absent) after a firing run.
